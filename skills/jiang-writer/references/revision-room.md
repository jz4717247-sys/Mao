# Revision Room

修订时一次解决一个层级。若结构尚未成立，不要先花时间磨每句对白。

## Pass 顺序

| Pass | 主要问题 | 允许改动 |
|---|---|---|
| 0. Brief / Canon | 是否理解了用户要的剧、格式与硬锁 | 澄清假设，不改故事 |
| 1. Engine / Structure | 剧集能否持续、本集是否有因果运动 | 季弧、故事线、场景增删与排序 |
| 2. Character / Relationship | 选择是否来自人物矛盾，关系是否变化 | 动机、策略、关系转向 |
| 3. Voice / Dialogue | 声纹、潜台词、曝光与口语性 | 台词、动作行、场内节奏 |
| 4. Continuity | 时间、知识、状态、规则和 setup/payoff | 修复事实、承接和必要铺垫 |
| 5. Production | 时长、预算、地点、演员、特技和覆盖 | 合并、拆分或视觉化场景 |

若某个后置 Pass 暴露前置层级问题，退回相应 Pass，不用台词补丁掩盖。

## Notes 处理

为每条 Note 标记：

- 来源与原始措辞。
- 它指出的症状。
- 推测的根因。
- 影响范围。
- 与 canon、引擎或其他 Note 的冲突。
- 采纳、部分采纳、暂缓或否决。

不要把执行者的一句解决方案误当成唯一问题定义。例如“加一场解释戏”可能真正反映的是人物选择不清楚。

## Table Read Pass

需要朗读感检查时：

1. 标出读者第一次失去因果的位置。
2. 标出角色需要额外解释才能完成的句子。
3. 标出连续独白、轮流发言和不自然的称呼。
4. 记录笑点、停顿或情绪转向是否落在预期位置。
5. 区分表演问题、文字问题和结构问题。

不要仅凭朗读时长机械删句。先判断时长来自信息重复、动作密度、停顿设计还是页面格式。

## 交付版本

- **Clean Draft**：只含可交付正文。
- **Notes Draft**：正文外附按优先级整理的 Notes。
- **Change Log**：只记录会影响后续协作的实质变更。
- **Redline Summary**：概述增删改原因，不伪造逐字修订痕迹。
