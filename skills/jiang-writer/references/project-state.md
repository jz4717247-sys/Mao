# 项目状态与断点续写

多集项目跨越多个会话。会话结束时，canon lock、已定稿集数、待办 Notes、账本状态全部留在对话上下文里——换一个会话就丢了。丢 canon 的代价不是重写一段，是新写的集数和已定稿的集数对不上。

本文管**项目层面的状态持久化**：做到哪了、锁了什么、哪些产物已经过期。与另外两本账本互补：

| 账本 | 管什么 | 文件 |
|---|---|---|
| 连续性账本 | 事实对不对得上（谁知道什么、伤在哪、几点） | [continuity-and-story-ledger.md](continuity-and-story-ledger.md) |
| 冲突装置账本 | 是不是又来一遍（换皮重复） | [anti-repetition.md](anti-repetition.md) |
| **项目状态** | **做到哪了、锁了什么、哪些产物已过期** | **本文** |

加载时机：跨会话的多集项目；用户说"接着上次""继续写""这个项目做到哪了"。单集、单场、一次性诊断任务不必建状态文件——为一场戏建账本是形式主义。

## 状态不是流程

本文**不引入线性阶段机**。jiang-writer 按模式路由（见 SKILL.md 任务模式表），用户要哪一档跑哪一档；状态文件记录**已经发生了什么**，不规定**接下来必须做什么**。

不得因为状态文件显示"Series Bible 未完成"就拒绝写某一场戏，也不得据此要求用户补做前置文档。用户跳过的阶段是用户的决定，状态文件如实记为 `skipped`，不当作缺陷反复提醒。

## 状态文件

项目工作目录下 `.jiang-state.json`，结构见 [project-state.json](../assets/templates/project-state.json)。核心分区：

- **project**：形态约束（类型、时长、季集数、平台、serialized/procedural、语言、分级）。这些是 SKILL.md"建立创作约束"一节提取的内容，落盘后不必每次会话重问。
- **canonLock**：用户已确认的人物、关系、世界规则、时间线、结局方向、叙事禁区。**最重要的一区**——断点续写的价值主要在这里。
- **artifacts**：各产物的文件路径（bible、season board、逐集大纲、逐集正文、声纹卡、两本账本）。
- **progress**：逐集各 pass 的状态、跨集审查进度。
- **decisions**：Showrunner 裁决记录与悬置决定。

## 恢复流程

会话开始时若发现 `.jiang-state.json`：

1. 读取并在**一段话内**汇报：项目形态、进度（第几集、什么状态）、canon lock 要点、有无 stale 产物、有无悬置决定。不要把整个 JSON 打印给用户。
2. 询问本轮要做什么。不要自动续写下一集——用户可能是回来改第二集的。
3. canon lock 直接生效，**不重新征求确认**；但若用户本轮的要求与 canon 冲突，先指出冲突再执行（同 SKILL.md canon lock 规则）。

状态文件与实际产物冲突时（记为 `done` 但文件不存在、或正文比状态新），**以实际文件为准**，修正状态并告知用户。不得依据过期状态覆盖用户已改的正文。

## Pass 状态词表

每集每个 pass 取四值之一：

- `none`——没做过。
- `draft`——做过但未定稿，可继续。
- `done`——已定稿。
- `stale`——做过，但上游改了，需要复核。

跟踪的 pass：`outline`、`script`、`critic`、`voice`、`humanize`、`continuity`、`device`、`compliance`（竖屏项目）、`director`（进入制作时）。项目用不到的 pass 记 `n/a`，不必凑满。

## 陈旧传播

改上游必须标下游 stale，否则状态文件会谎报"全部完成"。依赖链：

```
canonLock ─→ series bible ─→ season board ─→ outline(N) ─→ script(N) ─→ 各 pass(N)
voiceCards ─────────────────────────────────────────────→ voice(全集)
装置账本 ──────────────────────→ outline(全集)
```

规则：

- 改 canon（改名、换关系、改世界规则、改结局方向）→ 全项目所有产物标 stale，并**立即报告影响范围**。这是最贵的一种改动，用户有权在改之前知道代价。
- 改 season board 或某集大纲 → 该集及之后受影响集的 `script` 与各 pass 标 stale。
- 改某集正文 → 该集的 `critic`／`voice`／`humanize`／`continuity` 标 stale；若改动触及后续集依赖的事实，该事实的下游集也标 stale。
- 改声纹卡 → 全部已完成集的 `voice` 标 stale（不必立刻重跑，标记即可）。

**stale 不等于必须重做**。它是"这里没被复核过"的提示，交付前用户或 Showrunner 决定跑不跑。把 stale 当强制返工同样是形式主义。

## 跨集审查锚点

SKILL.md 规定季集数 >5 时每五集做一次跨集审查。状态文件记 `lastCrossEpisodeReview`（上次审查覆盖到第几集），跨会话不丢。当 `已完成集数 − lastCrossEpisodeReview ≥ 5` 时提示该做审查，**提示一次即可**，用户拒绝就记录并继续，不反复催。

## 维护成本

状态文件在会话结束、单集定稿、canon 变更后更新，不必每答一句就写盘。字段只填项目实际用到的，空字段留 `null` 而不是编内容。

用户没要求建状态文件、或明确说不要时，不建——正常写稿即可，本文不生效。
